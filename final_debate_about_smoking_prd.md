# Final Debate about Smoking

## Build-ready PRD / system spec for V1

**Status:** Draft for implementation  
**Product type:** Chat-first web app  
**Positioning:** Debate-based smoking cessation program  
**Inspiration:** Allen Carr-style principles, but delivered through live adversarial dialogue, memory, and staged progression rather than static reading  
**Audience:** Cigarette smokers only for V1  
**Core promise:** Help the user realize they are a non-smoker by dismantling the belief that cigarettes provide genuine value.

---

## 1. Product vision

### 1.1 Core idea
Final Debate about Smoking is a finite, structured, chat-first cessation program built around a simple thesis:

> Smokers do not need more platitudes, more guilt, or more generic support. They need their reasons for smoking examined, challenged, contradicted, and dismantled until the addiction loses psychological legitimacy.

This is not a generic quit companion. It is not a habit tracker. It is not a therapist replacement. It is not a medical service. It is a coach running a method.

The product begins not with “quit now,” but with a challenge:
- Do you actually like cigarettes?
- What do you think they do for you?
- What happened when you tried to quit last time?
- Which part was chemical, and which part was the story you told yourself?

The user is invited to bring resistance. The product should not fear debate. Debate is the front door.

### 1.2 The experience we want
The product should feel:
- warm toward the smoker
- unsparing toward the addiction
- lucid, calm, persuasive, and psychologically sharp
- repetitive in a useful way, but not robotic
- structured, but not sterile
- collaborative in tone, authoritative in direction

The user should feel:
- heard
- understood
- intelligently challenged
- less alone
- less ashamed
- increasingly unable to defend smoking honestly

### 1.3 Emotional north star
By the end of the program, the ideal user no longer feels:
- “I am resisting something I still love.”

Instead they feel:
- “I can now see that I never truly enjoyed it in the way I thought.”
- “I am not losing anything.”
- “I have been released, not deprived.”
- “I am a non-smoker.”

## 2. Product thesis

### 2.1 Main psychological thesis
Smoking persists because two systems combine into a trap:

1. **Narrative dependence**
   - beliefs
   - rationalizations
   - fears
   - identity
   - social myths
   - false interpretations of relief, stress, boredom, concentration, relaxation, pleasure

2. **Chemical dependence**
   - nicotine withdrawal loop
   - craving / relief cycle
   - anticipation and reinforcement

Each system is manageable on its own. Together they present as a lifelong prison.

The product’s job is to separate them, explain them, personalize them, and dismantle them.

### 2.2 Main mechanism of change
The system does **not** primarily help the user suppress desire.

It aims to **remove the perceived value of smoking**.

This is closely aligned with the source method’s emphasis that smokers are trapped by nicotine plus brainwashing, and that the real task is to remove the desire to smoke rather than rely on willpower or substitutes. The book repeatedly frames the smoker’s fear, false beliefs about stress/relaxation/concentration, and the illusion of sacrifice as the central mechanism to resolve. fileciteturn0file0

### 2.3 Differentiation
Most existing quit products:
- tell
- reassure
- prescribe
- track
- nag

Final Debate about Smoking should:
- interrogate
- surface contradictions
- use the user’s own evidence against the addiction
- carry memory across sessions
- gate progression by understanding, not mere time elapsed

Books and current apps often work as one-way doctrine. This product should work as a structured, adversarial, adaptive conversation.

## 5. User model

### 5.1 Primary user state
The core user does not enter as a compliant student.
They enter as a debater with one or more of the following positions:
- “I know smoking is bad, but I still like it.”
- “It helps me relax.”
- “It helps me think.”
- “Withdrawal is the real problem.”
- “I’ve tried quitting and it was horrible.”
- “I know it’s irrational, but it feels necessary.”

### 5.2 User’s felt dilemma
The smoker often feels:
- ashamed but defensive
- unconvinced by slogans
- tired of guilt-based messaging
- afraid of deprivation
- skeptical of generic coaching
- trapped between wanting freedom and wanting the cigarette

### 5.3 What the product must never imply
The product must never make the user feel:
- stupid for being addicted
- morally weak
- dirty as a person
- hopeless
- dismissed

The addiction is the target, not the smoker.

## 6. Core product principles

1. **Debate is the entry point.**  
   Resistance is not a bug. Resistance is material.

2. **Let the user speak first.**  
   Extract their theory of smoking before teaching yours.

3. **Socratic until useful, explanatory when needed.**  
   The system should not remain trapped in endless questioning.

4. **Truth over appeasement.**  
   The system can contradict the user directly when necessary.

5. **Warm toward the addict, sharp toward the addiction.**

6. **Progression is conceptual, not purely temporal.**

7. **Unresolved beliefs are deferred, not faked away.**

8. **The program has a spine.**  
   It is collaborative in tone, but not negotiable in mission.

9. **No premature quitting.**  
   The user should not be encouraged to turn this into another willpower attempt before the method has worked through key beliefs.

10. **The app should feel cumulative.**  
    Users must be shown what has been learned, what remains doubtful, and how their own past statements are now being interpreted.

## 7. Program structure

### 7.1 Shape
- finite program
- approximately 2–3 weeks in natural usage
- not strictly day-based
- actual progression driven by module completion and conceptual readiness

### 7.2 Overall flow
1. marketing hook / debate entry
2. intake and smoking narrative extraction
3. early belief challenge and motivation building
4. program commitment gate
5. structured modules
6. cumulative learnings and re-testing
7. final cigarette ritual
8. refund unlock
9. post-program static recap / restart path if needed

### 7.3 Progression philosophy
The user does **not** move forward just because time passed.
The user moves forward because enough of the current terrain has been worked through.

This means the system should track:
- which beliefs surfaced
- which contradictions were tested
- which concepts were understood
- which objections remain active
- whether the user’s responses in derivative tests show real change

## 8. Proposed module sequence for V1

This sequence should be implemented as the initial roadmap. It is inspired by the source method’s chapter arc, especially the repeated dismantling of stress, boredom, concentration, relaxation, brainwashing, the illusion of pleasure, the role of fear, and the idea that nothing is being given up. fileciteturn0file0

### Module 0 — The Challenge
**Goal:** Get the user talking, not complying.

Questions:
- Do you actually like cigarettes?
- Why do you smoke if you know the costs?
- What happened when you tried to quit before?
- What do cigarettes do for you that nothing else does?

Outputs:
- initial smoking narrative
- defended beliefs inventory
- resistance profile
- initial contradiction opportunities

### Module 1 — The Trap
**Goal:** Establish that the user is not uniquely broken; the trap has structure.

Themes:
- nobody sets out wanting lifelong dependence
- the trap is subtle
- the smoker’s conflict is not mysterious weakness
- the addiction has two parts: narrative + chemical

Outputs:
- normalized but not excused view of addiction
- first reduction in shame and fatalism

### Module 2 — Nicotine vs Meaning
**Goal:** Separate chemical dependence from the stories built around it.

Themes:
- withdrawal loop vs interpretation of withdrawal
- relief is not the same as benefit
- the cigarette appears to solve discomfort it helped create

Outputs:
- belief shift around craving / relief cycle
- first direct challenge to “I enjoy it”

### Module 3 — The Illusions of Relief
**Goal:** Dismantle false benefits.

Subthemes:
- stress
- relaxation
- concentration
- boredom
- confidence
- social ease

Outputs:
- user-specific map of false functions assigned to cigarettes

### Module 4 — What You Think You’re Giving Up
**Goal:** Break deprivation framing.

Themes:
- fear of missing out
- fear of identity loss
- fear of social loss
- fear that life becomes flatter
- the idea that quitting means sacrifice

Outputs:
- explicit language reframing quitting as release, not loss

### Module 5 — Why Prior Quits Failed
**Goal:** Recode previous failures.

Themes:
- not lack of character
- not proof of impossible addiction
- failed attempts as failed framing
- willpower attempts preserve the illusion of loss

Outputs:
- prior attempt reinterpretation
- lower fear about quitting

### Module 6 — The Last Cigarette Logic
**Goal:** Prepare the user for decisive transition.

Themes:
- why not to quit early
- why “just one” matters
- why waiting forever is another trap
- final identity shift

Outputs:
- readiness assessment
- final blockers surfaced

### Module 7 — Final Ritual
**Goal:** Mark the deliberate end.

Elements:
- final cigarette reflection
- explicit meaning-making
- statement of release
- ritual confirmation
- refund unlock

### Module 8 — Static Aftercare / Restart Logic
**Goal:** Minimal post-program layer.

Functions:
- summary of what the user learned
- top known relapse rationalizations
- path to restart if they resume smoking
- optional check-ins at 3 days, 3 weeks, 3 months for internal tracking only

## 9. Conversation design

### 9.1 Conversation style
The assistant should sound:
- calm
- clear
- psychologically literate
- warm but not cuddly
- direct when needed
- repetitive with variation
- never flustered by user arguments

### 9.2 Conversation strategy
Every module conversation can use this loop:

1. **Elicit**  
   Ask the user for their belief or lived example.

2. **Clarify**  
   Mirror the exact logic back in their words.

3. **Compress**  
   Ask narrower questions that force the belief into a testable structure.

4. **Contradict**  
   Identify the reversal, inconsistency, or false inference.

5. **Explain**  
   If the user does not arrive there, teach the point clearly.

6. **Restate**  
   Reformulate the new truth, ideally using the user’s own examples.

7. **Test**  
   Ask derivative questions that probe whether the user actually metabolized the point.

8. **Commit to state**  
   Mark beliefs as resolved, weakened, or deferred.

### 9.3 When to contradict directly
The assistant may directly contradict the user when:
- the user is defending a known smoking illusion
- the user is stuck in circular rationalization
- soft reframing has failed
- clarity matters more than tact in that moment

It should do so without contempt.

Example style:
- “No. That is not relaxation. That is temporary relief from a tension the addiction helped create.”
- “You are describing relief, not benefit.”
- “That sounds true from inside the addiction, but it does not hold up when examined.”

### 9.4 Resistance handling
Use three layers:

**Layer 1: Accurate mirroring**  
Make the user feel understood.

**Layer 2: Narrow contradiction**  
Reduce the claim to a smaller, testable idea.

**Layer 3: Structured deferral**  
If unresolved, mark it as a belief to revisit later rather than forcing fake agreement.

### 9.5 Repetition strategy
Repetition is useful and should be allowed deliberately, but with varied wording.
The system should revisit the same core truths from multiple angles.

No LoRA or fine-tune is needed for V1. Prompting, memory, and evaluation are sufficient.

## 10. Prompt architecture

V1 should use prompt-layering rather than fine-tuning.

### 10.1 Global system prompt
Responsibilities:
- define product identity
- define tone
- define non-goals
- define stage discipline
- define how contradictions are handled
- define safety boundary

### 10.2 Module prompt
Each module should have a dedicated instruction layer specifying:
- module objective
- beliefs being targeted
- common user objections
- what counts as sufficient understanding
- what should be refused/deferred because it belongs to later modules

### 10.3 Memory insertion prompt
Before each session, inject:
- short user profile summary
- current module
- active beliefs
- deferred beliefs
- last module learnings
- tone notes if relevant

### 10.4 Summary prompt
After each session, generate:
- session summary
- beliefs strengthened / weakened / resolved / deferred
- evidence user gave
- notable contradictions surfaced
- recommended next moves

### 10.5 Stage-governor prompt
Separate layer that enforces:
- no premature module leakage
- partial answers only for future concepts
- progression based on readiness, not user impatience alone
- final ritual locked until prerequisites satisfied

## 11. Memory model

### 11.1 Memory goals
Memory should make the app feel cumulative, intelligent, and personally relevant.
The model must be able to say things like:
- “Last week you said smoking only helps when you are anxious. But yesterday you also described craving cigarettes after relaxed meals.”
- “You keep saying it helps you think, but your own story suggests you smoke before concentration tasks because you fear the craving, not because the cigarette improves thought.”

### 11.2 Memory classes
Store at minimum:
- smoking history
- quit history
- defended beliefs
- triggers / situations
- emotional interpretations
- contradictions surfaced
- module summaries
- readiness state
- ritual commitments
- user-specific phrases that can be reused later

### 11.3 Belief object schema
Each belief should be stored as a structured object.

Suggested schema:
```json
{
  "belief_id": "stress_relief",
  "label": "Smoking relieves stress",
  "user_wording": "A cigarette calms me down when I'm under pressure",
  "confidence": "high",
  "evidence_user_gave": [
    "after work",
    "after arguments",
    "when waiting for difficult calls"
  ],
  "contradictions_found": [
    "also smokes when relaxed after meals",
    "reports pre-cigarette tension rising when unable to smoke"
  ],
  "status": "weakening",
  "last_challenged_at": "timestamp",
  "defer_to_module": "illusions_of_relief"
}
```

### 11.4 Learning object schema
Suggested:
```json
{
  "learning_id": "withdrawal_not_benefit",
  "summary": "User now partly understands that relief from craving is not the same as a genuine benefit.",
  "source_module": "nicotine_vs_meaning",
  "strength": "medium",
  "evidence": [
    "user acknowledged cigarettes feel most valuable when deprived"
  ]
}
```

### 11.5 What not to store aggressively
The system should avoid storing excessive irrelevant conversational debris.
It should also avoid repeating back personal disclosures in a way that feels creepy or punitive.

Default rule:
- store what advances the program
- do not hoard everything

## 12. Progression logic

### 12.1 User-facing progression
Do **not** make progression feel like quantified self-gamification.
Avoid loud percentages.
Use a roadmap or chapter-like structure instead.

Recommended visible surfaces:
- current stage
- what has been understood so far
- what remains under examination
- next theme

### 12.2 Hidden progression
Internally, maintain:
- module readiness score
- belief-resolution state
- agreement / conviction score
- unresolved blocker count
- test-question performance

### 12.3 Module completion logic
Use **rules + model judgment**.

A module completes when:
- key prompts were attempted
- required concepts were covered
- derivative understanding tests were attempted
- essential beliefs are either resolved or deferred
- model judges the user has enough grounding to continue

### 12.4 Do not over-determinize
Avoid rigid systems like:
- exactly 5 questions only
- exact phrase match for agreement
- one-score thresholds with no nuance

The program should be structured, but not brittle.

---

## 13. Understanding tests

### 13.1 Purpose
At the end of each module, test real understanding instead of asking for explicit agreement.

### 13.2 Test design
Tests should be:
- derivative
- subtle
- applied
- slightly adversarial

Examples:
- “If smoking relaxes you, why do you feel pressure building before the cigarette?”
- “Why does a cigarette feel best after deprivation?”
- “What is the difference between ending craving and gaining a real benefit?”
- “Why might a smoker mistake relief for pleasure?”

### 13.3 Test outcomes
Possible outcomes:
- understood
- partly understood
- antagonistic / defensive
- unresolved

If unresolved:
- drive the point once more
- then defer it to later module treatment

## 15. Wallet / refund logic

### 15.1 Purpose of the wallet
The wallet is a commitment mechanism, not merely pricing.

It should be framed as:
- commitment to finishing
- seriousness filter
- proof that the product is confident in its method

### 15.2 Proposed logic
Flow:
1. user enters via debate / discovery
2. product builds enough motivation and confidence
3. product offers the structured program
4. user stakes money into wallet
5. user completes modules
6. user reaches final cigarette ritual
7. user confirms completion of ritual
8. refund unlocks

### 15.3 Philosophy
Desired messaging:
- We do not want your money if you are committed to finishing.
- If you fail to finish, you fund the people who do show commitment.
- If you complete the program and still do not quit, you still get your money back.
- If you do quit, you may optionally choose not to reclaim it.

### 15.4 Fraud posture
V1 should lean on trust and brand goodwill.
Do not over-engineer anti-fraud early.

### 15.5 V1 note
Wallet should be treated as a **secondary commercial layer** if build complexity threatens the core chat product. The core product must work without it. But it should be designed into the PRD now.

## 16. Safety and boundary behavior

### 16.1 Product identity boundary
This product is:
- a coach
- a program
- a method

It is not:
- a doctor
- a therapist
- a psychiatrist
- crisis support

### 16.2 Distress handling
If the user becomes significantly distressed:
- soften
- pause pressure
- stabilize
- avoid continuing the adversarial mode in that moment
- resume the program once the user is steadier

### 16.3 Severe symptoms
If the user reports severe anxiety, panic, depression, or similar destabilization:
- do not take broad responsibility
- avoid expanding into clinical management
- avoid medication advice
- encourage real-world support / medical guidance only as needed, minimally and clearly

### 16.4 Medical stance
For V1, do **not** recommend NRT, varenicline, or bupropion as a built-in product path.
The product philosophy here is deliberately non-NRT.

### 16.5 Off-topic conversation
Keep off-topic conversation minimal.
If it does not advance the program, redirect.

### 16.6 Human handoff
No human handoff required in V1.

## 17. Stage governance and information leakage

### 17.1 Rule
If the user asks about a later module:
- partially answer if useful
- do not fully collapse future learning
- redirect back to prerequisite reasoning

### 17.2 Why
This product is not just an LLM answering questions. It is an LLM embedded in a staged pedagogy.
If the assistant answers everything in full immediately, it can destroy the structure of the method.

### 17.3 Example behavior
- “That does matter, and we will get there. But right now I want to stay with the belief you just stated, because if that remains intact the later point will not land properly.”

## 18. System architecture proposal

### 18.1 Recommended stack direction
Use a web app first.

Suggested practical stack:
- **Frontend:** Next.js / React
- **Backend:** Python FastAPI or Node backend
- **Database:** Postgres
- **Structured state / caching:** Redis optional
- **LLM orchestration:** server-side prompt orchestration layer
- **Auth:** simple email / OTP or magic link
- **Analytics:** PostHog or equivalent
- **Jobs / nudges:** scheduled worker / cron
- **Admin tools:** internal protected dashboard

This is a recommendation, not a requirement.

### 18.2 Core backend services
1. **Conversation service**
   - manages chat turns
   - injects stage and memory context
   - returns structured response + metadata

2. **Stage governor**
   - enforces module rules
   - decides whether to progress or defer
   - prevents future-module leakage

3. **Belief tracker**
   - updates belief objects from conversation
   - changes status values
   - surfaces revisit candidates

4. **Summary engine**
   - writes session summaries
   - updates learnings
   - compresses memory context

5. **Program state service**
   - tracks module status
   - readiness score
   - test outcomes
   - ritual eligibility

6. **Notification service**
   - inactivity reminders
   - milestone prompts
   - optional 3-day / 3-week / 3-month check-ins

7. **Wallet/refund service**
   - stake state
   - refund unlock condition
   - payment status

### 18.3 Multi-agent recommendation
Use modular roles under the hood rather than one unconstrained monolith.

Suggested roles:
- **Debate Coach** — main user-facing conversational agent
- **Stage Governor** — hidden logic agent / rules layer
- **Belief Extractor** — structured parser from transcripts
- **Summary Curator** — compresses session learnings
- **Safety Stabilizer** — lightweight override for distress cases

Implementation can still be one model with multiple prompts / passes, but the architecture should conceptually separate these roles.

## 21. Evaluation plan

This product will fail if the bot becomes generic, contradictory, or stage-blind. Evals matter.

### 21.1 Core eval categories
1. **Belief extraction accuracy**
   - does the system correctly identify the user’s defended smoking beliefs?

2. **Contradiction quality**
   - does it surface the right contradiction?
   - does it avoid straw-manning the user?

3. **Stage discipline**
   - does it avoid prematurely leaking later-module content?

4. **Tone consistency**
   - warm toward smoker, sharp toward addiction
   - no contempt
   - no robotic flattening

5. **Summary quality**
   - are learnings coherent and reusable?
   - do summaries preserve program-relevant state?

6. **Belief-state consistency**
   - does the stored belief object match the actual conversation?

7. **Progression correctness**
   - does the user advance only when ready enough?

8. **Repetition quality**
   - does the system reinforce ideas without sounding broken?

9. **Safety stabilizing behavior**
   - does it soften and pause when the user is distressed?

10. **Final ritual gating correctness**
   - ritual locked before readiness
   - ritual unlocked after meaningful completion

### 21.2 Example eval scenarios
- user insists smoking relaxes them
- user is highly argumentative but intelligent
- user agrees too easily / superficially
- user becomes antagonistic at end-of-module test
- user asks future-module questions too early
- user expresses panic during quitting discussion
- user returns after 5 days inactive
- user claims earlier belief that contradicts stored memory

### 21.3 Human review process
Initially, log and review:
- random conversations
- failed module completions
- contradiction misses
- summary mismatches
- users who stall repeatedly on same belief

## 23. Task decomposition for an agentic build system

A builder agent should be able to split work into these streams:

### Stream A — Product spec codification
- convert module list into structured JSON / config
- define completion criteria per module

## 24. Copy and tone guardrails

### Must do
- sound certain without sounding pompous
- never shame the smoker
- speak as if the product understands addiction from inside
- use clean language, not clinical sludge
- occasionally repeat truths with varied phrasing

### Must not do
- become chirpy or gamified
- sound like generic self-help
- over-apologize
- get socially performative about health warnings
- ramble abstractly
- lose structure

### Tone formula
**Human warmth + rhetorical clarity + calm conviction**

## 26. Final summary

Final Debate about Smoking should be built as a **finite, stage-governed, belief-tracking, debate-based web app** that helps cigarette smokers quit by dismantling the stories that make smoking feel meaningful.

It should feel like a calm and intelligent confrontation with the addiction.
It should remember what the user said.
It should not let the user wriggle out with slogans.
It should not move forward just because a timer elapsed.
It should earn the final quit moment by changing what smoking means.

The V1 bar is not “build a perfect cessation platform.”
The V1 bar is:

> build a chat system that can carry the core anti-smoking method with enough structure, memory, tone, and progression logic that a user feels they went through something sharper and more personal than a book or a generic quit app.
